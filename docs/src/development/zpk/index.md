# 制品开发

本文面向制作、维护和发布面板应用的开发者。依据独立仓库 [w7panel-zpk](https://github.com/w7panel/w7panel-zpk) 当前工作区代码核对，日期为 2026-10-15。页面流程来自该仓库 `ui/`，不是 `w7panel-ui/`；安装执行由面板 Server 负责。

- 第一次操作：[制品库操作示例](../examples/zpk-product-workflow.md)。
- 开发独立应用的代码与构建示例：[应用开发示例](../examples/index.md)。

以下是静态源码核对结果，未向仓库推送、提交市场审核或安装到集群。截图仅供定位，实际字段以当前页面为准。

## 制品、镜像、Chart 和市场商品的关系

| 对象 | 负责什么 | 不能由它单独证明什么 |
| --- | --- | --- |
| 容器镜像 | 提供程序及运行环境 | 镜像推送成功不代表制品版本已发布 |
| 制品版本 | 保存 manifest、源码包、前端包和原始 Helm 附件等交付内容 | 保存配置不保证最终 Chart 打包成功 |
| 运行 Chart | 把制品转换为安装时使用的 Kubernetes 资源 | 打包成功不代表已经安装或应用健康 |
| 市场商品 | 维护展示、价格、授权及审核信息 | 商品提交不代表审核通过，也不代表安装成功 |

`charts/` 是 **ZPK 服务自身** 的部署包；业务制品的 Chart 由 `app/respo/logic/helm/` 生成，两者不能混用。

## 进入制品库

从面板中已安装的制品开发应用进入。官方部署可能提供固定入口，自建部署应使用自己的入口，不要把示例面板域名作为项目必需条件。

前端使用 Vue 3、JavaScript、Vue CLI、Vuex 和 Arco Design。制品列表路由为 `#/zpk`，版本页为 `#/zpk-version?id=制品标识`；后端业务接口前缀为 `/zpk/respo/`，不是面板 `/panel-api/v1/zpk/`。

微应用加载时会从面板注入的地址建立请求基址，并使用 ZPK 自己的 `X-Zpk-Token` 会话。通过面板微应用代理时还携带 `X-W7Panel-Token`。两种凭据及云端账号用途不同。

## 创建制品与基础信息

列表“添加制品”先填写标识。`POST /zpk/respo/add` 会创建制品及初始 **1.0.0** 版本，不必再创建同名版本。名称、介绍、分类等随后在版本页的基础信息区域维护。

标识有两层规则：

- 页面组件把标识拆成“作者前缀”和“业务标识”，两段新输入均只接受字母和数字，用一个 `-` 连接，例如 `acme-blog`。前缀不固定为 `w7`。
- 后端接受 `^[A-Za-z0-9]+(?:-[A-Za-z0-9]+)*$`，即多段字母数字用单个横线分隔；不能首尾横线、连续横线或带空格。创建接口为旧客户端保留下划线转横线兼容，这不等于页面允许输入下划线。

标识与根 manifest 的 `application.identifie` 必须相同。不要通过改 YAML 把现有制品变成另一份制品。

### 基础信息不是每个版本的独立副本

名称、描述、注解、单次安装、集群权限及创建站点等基础信息保存在制品级 `Setting.BaseInfo`。读取和发布时会覆盖根版本 manifest 中对应字段；旧数据没有该设置时才从 manifest 回退读取。

因此，修改基础信息不能按“仅影响正在编辑的版本”理解。分类也用于市场发布检查；自动发布商品时必须准备分类和绑定的云端账号。

## 版本管理

网页新建版本目前只接受 **`数字.数字.数字`**，例如 `1.0.1`。不要按旧说明在网页输入 `v1.0.0` 或 `1.0.0-beta.1`；后端接口的 `semver` 校验与网页限制不是同一层。

新版本从当前线上指向的版本复制 OCI 内容，不能假定会自动复制任意未发布版本的本地编辑。重复提交已有版本号只修改版本说明，不会再次复制源版本。新建后核对实际镜像、附件、子应用和参数。

创建版本记录与复制 OCI 不是同一事务：复制失败后可能已经留下版本记录，重提同一版本号也不会补做复制。源版本尚无 OCI manifest 时，复制函数直接跳过，因此创建成功不保证已经继承源文件。

| 页面状态 | 字段值 | 含义 |
| --- | --- | --- |
| 未发布 | `publish_status=-1` | 版本尚未完成发布 |
| 发布中 | `1` | 已进入后台运行 Chart 打包队列 |
| 已发布 | `2` | 后台打包成功，线上版本指针已更新 |
| 发布失败 | `3` | 查看 `publish_fail_reason`，修正后重新发布 |

列表兼容旧状态 `0`，返回时按已发布处理。“线上版本”取数据库指针，不是简单比较版本号大小；首次创建时已经有初始指针，不能只凭顶部卡片就认定完成过打包。发布后刷新列表核对版本状态，当前版本页没有持续轮询发布状态的实现。

## 后端包管理：先选类型

| 页面类型 | `application.type` | 配置重点 |
| --- | --- | --- |
| 原生应用 | `docker` | 镜像、多容器、工作负载、存储、端口、环境和脚本 |
| K8sYaml | `helm` | Helm 仓库或 tgz、values 覆盖、额外 YAML |
| 传统应用 | `tradition` | 语言、镜像模板、可选代码包、持久目录、运行命令、NGINX 和脚本 |
| 应用插件 | `app-plugin` | 选择传统应用、安装代码、共用存储及安装/卸载脚本 |
| 系统镜像 | `system-image` | 镜像版本、Sysbox 环境和根文件系统存储 |
| 网关插件 | `gateway-plugin` | Wasm 运行时、支持范围、默认配置及可选配置前端 |

`sidecar` 另有模板组合用途，不应当作普通应用类型套用安装流程。类型选择会删除不适用的配置；切换前保留当前 manifest 和附件信息。

### 原生应用

镜像必须是已存在、可被目标节点拉取的镜像。选择 Deployment、StatefulSet 或 DaemonSet；填写多容器的命令、参数、端口、环境变量、健康检查和挂载点。仅填写端口不等于公网可访问，还需匹配服务和网关规则。

源码 ZIP 与镜像是不同交付物。部分配置可生成安装时的构建 Job；发布制品不是通用的源码 CI，不能保证自动为任意源码构建业务镜像。没有构建需求时直接使用已发布镜像。

### 传统应用

当前实现生成自己的运行工作负载，不能继续描述为“只把代码安装到站点管理”。站点管理是可以集成的入口，不替代运行资源。

- 配置语言、镜像模板和可用版本，模板中的 `{version}` 根据安装参数替换。
- 代码包可选。打包时让安装内容直接位于 ZIP 根目录；代码运行目录为 `/www/wwwroot`。
- 运行命令在应用配置中设置；安装/升级脚本只在对应生命周期执行，不会因每次普通重启自动执行。
- 代码和站点配置使用安装时选择的 `PVC_NAME`，按域名分隔目录。
- 可选 NGINX 网关涉及工具子应用及其配置；系统重启文件恢复、插件文件优先级也有独立设置，不是任意持久卷的通用备份。

### 应用插件、系统镜像与网关插件

应用插件通过 hook Job 向所选传统应用安装内容，没有自己的常驻业务工作负载，也不创建独立站点 PVC。插件包要保留安装所需目录，例如 ZIP 根目录直接包含 `addons/`。启用文件优先级时系统可恢复覆盖文件；未启用时不能承诺卸载会自动清理所有代码。

系统镜像需要相应 Sysbox 组件、版本和持久存储，不能按普通业务镜像处理。编辑器补齐 `IMAGE_VERSION`、`PVC_NAME` 等参数。

网关插件当前运行时为 `higress-wasm/v1`，生成 WasmPlugin。全局支持、规则支持和默认启用分别配置；配置前端与插件通过相同的 `w7.cc/group-name` 标签关联，不使用旧关联注解。

## 前端包、管理端与菜单

“前端包管理”维护 `web` 与 `bindings`。前端 ZIP 的根目录应直接包含构建后的入口及资源，不多包一层 `dist/`。

管理端配置包含角色、菜单、加载方式、内部/外部后端、请求转发和 `frontend_props`。静态前端托管与 iframe 是不同加载方式；iframe 只保存对应的 Query 转发，不应假定会像后端代理一样附加任意请求头。

生成 MicroApp 的条件为：**`web.url` 非空，或任一 Binding 有菜单项**。因此：

- 只有运行镜像、没有前端地址和菜单的制品，不会仅因后端存在就生成管理入口。
- 外部页面或 iframe 菜单可以不上传本地前端 ZIP，不能写成“没有 ZIP 一定没有菜单”。
- 有前端地址也不保证每个账号看得到菜单，还要核对角色、菜单、加载方式和面板授权。
- 前端 ZIP 不直接塞进最终运行 Chart，Chart 保存 MicroApp 配置，前端资源通过附件链路获取。

请求头、Query 和前端 props 各有用途。仅注入应用需要的上下文，不把面板登录凭据、ZPK 会话、OIDC access token 或厂商密钥视为同一种值。

## 启动参数、子应用与安装依赖

安装参数在 `platform.startParams` 声明，值还需要被容器环境、脚本或 Chart 模板使用；添加一个表单参数不等于程序自动读取它。

普通内部子应用由同一版本中的 `<子标识>/manifest.yaml` 提供；外部依赖通过 `platform.depends` 单独安装或复用。远程导入子应用会下载指定版本的完整 manifest 及附件，随后由编辑页保存到当前版本。仅填写 `from` 不等于已经完成内嵌打包。

主应用的 `application.order=0`，子应用按当前列表维护为 `1...n`。该值用于同组 MicroApp 展示，**不是容器启动顺序**。

## 提交、发布与下架

1. 在后端/前端编辑页核对配置后点击“确定提交”。普通完成分支先保存 manifest，成功读取该版本 Info 后才请求 `/respo/publish`；Info 读取失败会有限重试，耗尽后不继续发布。跳转子文件编辑或仅保存分支不会走同样的发布流程。
2. 发布先同步打包到 OCI。开启“自动发布到制品市场”时，还会调用商品发布服务；缺少云端账号或账号归属不一致会失败。
3. 后台队列生成最终运行 Chart。看到“发起打包成功”只说明请求阶段完成，等待版本状态变为“已发布”。
4. 市场审核另查审核状态，安装另查面板 AppGroup 状态与实际访问结果。

各阶段不是跨数据库、OCI、市场的整体事务。后续失败时，前面的配置或 OCI 上传可能已完成；修复后先确认已有状态再重试。

“修改成功”在发布之前显示；发布请求的错误还可能被页面捕获后继续跳转。必须查看版本最终状态，不能只依据提示或页面跳转。

版本下架需要存在更早创建且已发布的版本，按记录 ID 回退并重新发起该版本发布，不是按语义版本号自动选择最大值，也不会让已经安装的应用自动降级。重新发布失败时按错误提示手工处理。

## 命令行上传附件

当前 CLI 注册 `login`、`use`、`attach`、`push`、`list`，不提供通用的 `zpk build` 或 `zpk publish` 命令。页面“发布设置”给出当前仓库的登录参数；凭据使用仓库账号，不用面板 JWT 代替。

```bash
# 以下为操作示例，替换工具名、地址、账号和密码；push 会写远端仓库
./zpk_linux_amd64 login --username=YOUR_USER --password=YOUR_PASSWORD --host=YOUR_REGISTRY
./zpk_linux_amd64 use acme-blog
./zpk_linux_amd64 attach add --path=./frontend.zip --type=frontend
# 子应用附件追加 --sub_artifact=acme-worker
./zpk_linux_amd64 push
```

附件类型为 `frontend`、`backend`、`helm`。`use` 会清空当前待上传附件选择，`push` 要求至少选一个附件。未显式选择 OCI tag 时，CLI 尝试从远端最新版本递增 patch；未取得版本时使用 `1.0.0`。推送事件会导入/更新版本，但不会自动完成网页发布与市场审核，仍需回版本页确认。

## 发布验证与排查

| 现象 | 核对方向 |
| --- | --- |
| 新版本内容不对 | 新建版本的复制来源、版本号、附件和镜像 tag，不假定未发布本地编辑已复制 |
| YAML 修改后又被覆盖 | 制品级基础信息是否覆盖了版本字段；类型切换是否重建了配置 |
| 发布失败 | 版本失败原因、OCI 上传、远程 Chart/Sidecar、分类及云端账号 |
| 无前端菜单 | `web.url`/Binding 菜单、角色、加载方式、MicroApp 与实际资源路径 |
| 配置保存成功但市场不可见 | 自动发布开关、商品与审核状态，不只看配置保存提示 |
| 安装后不能访问 | 面板安装状态、运行事件、日志、域名、后端端口和凭据 |

最终验证应覆盖新装、从旧版升级、所选依赖、持久数据及卸载影响。不要把发布接口成功、Chart 渲染通过或顶部“线上版本”卡片当作完整运行验证。
