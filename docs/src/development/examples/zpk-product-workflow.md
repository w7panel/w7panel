# 制品库操作示例

本文说明应用开发完成后，如何在制品库中添加制品、配置版本并提交发布。适用于已经准备好运行镜像、代码包、前端包、Helm 包或额外 YAML 的应用。

从自己的面板进入已安装的制品开发应用。以下截图用于定位大致区域，具体字段以安装版本为准。

## 操作前准备

| 应用形态 | 需要准备 |
| --- | --- |
| 容器应用 | 可拉取的镜像、端口、环境变量、启动命令和存储需求 |
| 传统应用 | 运行镜像模板与版本、按需提供源码 ZIP、运行命令及生命周期脚本 |
| Helm / K8sYaml 应用 | Chart 仓库信息或 tgz，以及 values 和额外 YAML |
| 应用插件 | 对传统应用执行安装、升级等操作所需代码或脚本 |
| 网关插件 | Wasm 地址、阶段、优先级和 JSON 默认配置 |
| 系统镜像 | 根文件系统镜像、版本、存储与相应运行环境 |

面板入口可使用前端 ZIP，也可以配置外部地址或菜单入口；不要把前端 ZIP 当作所有制品的必备附件。镜像推送和制品发布是不同操作。

开始前先准备以下信息：

| 项目 | 说明 |
|------|------|
| 制品标识 | 页面将作者前缀与业务标识两段字母数字用横线连接，例如 `acme-blog`；前缀不固定为 `w7` |
| 制品名称 | 展示给用户的应用名称 |
| 分类 | 按应用场景选择后台应用、系统组件等分类 |
| 代码包 | 后端包、传统站点代码包、前端包、Helm 包或额外 YAML，按应用形态提供；有面板页面时通常需要前端包 |
| 入口信息 | 面板菜单名称、访问路径、控制台入口、是否支持 iframe |
| 运行配置 | 应用端口、环境变量、启动参数、网关域名转发规则 |
| 依赖关系 | 当前制品安装前需要依赖的其他制品 |
| 版本说明 | 当前版本的变更内容、安装说明和注意事项 |

上传前确认交付内容可以追溯到 Git tag、commit 或构建记录；正式版本避免使用临时包和调试配置。

## 添加制品

列表页添加弹窗提交制品标识。当前页面使用两段字母数字输入并用 `-` 连接，前缀不强制为 `w7`；后端还接受多段字母数字用横线连接的标识。不要用页面输入限制概括整个 API 协议。

创建成功即有未发布的 `1.0.0`，不需要再创建同名初始版本。随后维护名称、描述、图标和发布设置。名称、描述、注解、单次安装、集群权限、站点注册等制品级基础信息会在保存或加载时应用到版本配置，不能只在旧 manifest 中改值就认为生效。

| 字段 | 填写建议 |
| --- | --- |
| 标识 | 保持稳定，使用自己的作者前缀与业务名称 |
| 名称 | 使用用户能理解的应用名称 |
| 分类 | 按实际用途选择，自动发布市场时需要补齐 |
| 描述 | 说明功能、安装要求和使用限制 |

## 进入版本管理

版本页新增版本接受 `数字.数字.数字`，例如 `1.0.1`。当前网页不接受 `v1.0.1` 或 `1.0.1-beta`。服务端采用语义版本校验，范围与网页不同。

新版本从当前指针所指版本复制 OCI 内容；不要假设任意未发布本地编辑都能成为复制来源。已有版本号只修改说明，不会再创建一个版本。

复制失败时可能已经留下新版本记录，重复提交不会重做复制；源 OCI 内容不存在时也可能跳过复制。继续编辑前核对实际文件和附件。

应用编辑器支持容器、传统、Helm、应用插件、网关插件和系统镜像等六类作者配置。`sidecar` 是打包契约中的辅助类型，不应当成普通编辑类型。切换类型后核对遗留 Helm 配置，打包分流不只检查应用 type。

![版本管理](/examples/zpk/02-version-management.png)

## 配置后端包管理

后端包管理负责应用的运行方式、文件、端口和安装配置。先选类型，再按类型补充内容。管理页面与菜单在前端配置中单独维护。

### 选择代码配置类型

| 类型 | 需要准备 |
| --- | --- |
| 原生应用 | 已发布镜像、容器与服务配置 |
| 传统应用 | 运行环境模板、版本、可选源码包和运行命令 |
| K8sYaml | Helm 仓库或包、values 和额外 YAML |
| 应用插件 | 目标传统应用、安装代码或脚本 |
| 网关插件 | Wasm 地址、插件参数和可选配置页面 |
| 系统镜像 | 根文件系统镜像和所需运行环境 |

### 原生应用配置

先根据应用运行方式选择应用类型：

| 应用类型 | 适用场景 |
|----------|----------|
| 无状态应用 | 不需要持久化本地状态，适合大多数 API 服务、后台任务入口 |
| 有状态应用 | 需要稳定存储或实例身份，适合数据库、队列、带本地状态的服务 |
| 守护进程应用 | 需要在节点上长期运行，适合节点级采集、代理、巡检类服务 |

原生应用的应用配置字段较多，日常发布制品时优先确认以下常用项即可：

| 配置项 | 使用说明 |
|--------|----------|
| 应用镜像 | 填写应用运行镜像，例如 `nginx:1.28` 或制品构建后的业务镜像；镜像仓库、拉取策略按实际镜像来源配置 |
| CPU/内存限制 | 按服务资源需求填写；不确定时先使用保守值，避免安装后占用过高 |
| 数据卷 | 应用需要持久化文件、缓存或配置时添加；纯无状态服务可以不配置 |
| 挂载点 | 将数据卷挂载到容器内目标路径；注意路径不要覆盖镜像内必要目录 |
| 环境变量 | 填写运行参数、开关和非敏感默认值；支持批量编辑 `key=value` |
| 暴露端口 | 填写容器对外提供服务的端口和协议，例如 HTTP 服务常见为 `80` 或 `8000` |
| 运行命令 | 需要覆盖镜像默认启动命令时填写；不需要覆盖时保持空 |

![应用配置基础项](/examples/zpk/03-app-config-basic.png)

高级设置中常用的是挂载点、环境变量、暴露端口和运行命令。端口只声明容器服务端口，不等同于外部访问入口；后端请求如何转发，需要在网关域名转发设置中单独配置。

![应用配置高级项](/examples/zpk/04-app-config-advanced.png)

常用项填写建议：

| 配置项 | 使用说明 |
|--------|----------|
| 镜像 | 使用当前版本对应的正式构建产物，避免引用开发机临时镜像 |
| 存储 | 只有应用确实需要持久化时添加数据卷；否则保持无状态更容易升级和扩缩容 |
| 挂载 | 目标路径要和应用代码读取路径一致，例如 `/data`、`/app/config` |
| 端口 | 和应用实际监听端口一致；后续网关域名转发设置会基于该端口做请求转发 |
| 环境变量 | 只放运行必需项；密码、密钥等敏感值不要写成公开默认值 |
| 命令 | 仅在镜像默认 `ENTRYPOINT` 或 `CMD` 不满足时填写 |

数据卷声明不保证自动创建持久存储：Deployment 需确认已有存储或安装时选择，StatefulSet 的声明模板另行处理。

### 传统应用配置

传统应用会生成自己的运行资源，不能理解为仅把代码装到站点管理中。填写镜像模板、运行版本、代码包及应用配置中的运行命令。代码通常位于 `/www/wwwroot`，存储按站点目录组织，可选配 NGINX 工具子应用。

安装与升级脚本在对应生命周期执行，不等同于每次容器启动命令。重启恢复、插件优先级和卸载恢复需要单独核对，不能承诺卸载一定自动恢复所有文件。

![传统应用配置](/examples/zpk/03-traditional-app-config.png)

| 配置项 | 说明 |
| --- | --- |
| 环境类型与版本 | 根据程序要求选择，镜像模板中的版本按安装参数替换 |
| 代码包 | 按需上传，安装内容直接放在 ZIP 根目录 |
| CMD | 应用的运行命令，与安装和升级脚本分别配置 |

### K8sYaml 配置

选择“K8sYaml”后，不需要进行原生应用配置。K8sYaml 类型面向已经准备好 Kubernetes 部署描述的应用，支持上传 Helm 包和额外 YAML。

![K8sYaml 配置](/examples/zpk/03-k8syaml-config.png)

K8sYaml 常用配置：

| 配置项 | 说明 |
|--------|------|
| 启用 Helm 配置 | 需要通过 Helm Chart 安装时开启；只使用额外 YAML 时可不启用 |
| Chart 包来源 | 支持选择 Helm 仓库或 Helm 下载包 |
| Chart 包地址 | 选择 Helm 下载包时填写或上传 Chart 包地址 |
| 安装配置 | 通过键值方式补充 Helm values 覆盖项 |
| YAML 配置 | 上传或填写额外 YAML，支持添加多个 YAML 配置 |
| 标题 | 为额外 YAML 添加可识别名称 |
| YAML | 填写具体 YAML 内容 |

K8sYaml 适合已经有标准部署描述的应用。发布前应确认 Helm 包、安装配置和额外 YAML 对应同一个版本，避免 Chart 和 YAML 引用的镜像或参数不一致。

可选择 Chart 仓库或 Chart 下载包，配置 values 覆盖和额外 YAML；也支持只有额外 YAML 的生成路径。自带 Chart 由作者负责模板、PVC、账号权限及 Sidecar 插槽，平台不会自动修复所有模板。

### 插件与系统镜像

应用插件使用 hook Job 操作传统应用存储，没有独立常驻工作负载。网关插件生成 Higress WasmPlugin，需提供有效 Wasm URL，优先级范围为 0–1000，默认配置必须是 JSON 对象。系统镜像还涉及根文件系统挂载、Sysbox 运行环境和持久存储，应在目标测试环境验证。

## 配置启动参数、域名转发和依赖

完成代码配置类型对应的内容后，再按应用需要配置启动参数、网关域名转发、安装依赖和子应用。不是所有制品都需要这些配置；纯静态或纯后端内部能力可以只保留必要项。

### 启动参数设置

启动参数用于把安装时需要用户决定的值暴露出来，例如服务端口、数据目录、功能开关、初始化账号或外部服务地址。参数应尽量使用清晰的名称和默认值，让安装者不需要理解底层部署细节也能完成配置。

启动参数建议：

| 项目 | 说明 |
|------|------|
| 参数名称 | 使用业务可理解的名称，不要只写内部变量名 |
| 默认值 | 能安全运行的默认值可以提供；敏感信息不要提供公开默认值 |
| 必填项 | 没有默认值且应用启动必需的参数应标记为必填 |
| 说明文案 | 写清楚参数用途、格式和影响范围 |

### 网关域名转发设置

网关域名转发设置用于配置后端请求入口和转发规则。需要让前端或外部入口访问后端服务时，在这里声明域名、路径、转发目标和匹配规则。

注意：制品页不会直接展示或维护 Service、Ingress 等底层资源明细。开发者只需要按制品库提供的网关域名转发设置填写访问规则。

常见配置：

| 配置项 | 说明 |
|--------|------|
| 域名 | 需要通过域名访问后端服务时填写 |
| 请求路径 | 前端或外部访问使用的路径 |
| 转发目标 | 指向后端应用的服务端口 |
| 匹配规则 | 按路径、前缀或页面提供的规则转发 |

### 安装依赖

安装依赖用于声明当前制品依赖的其他制品。比如当前应用需要数据库、缓存、消息队列或某个基础组件先安装完成，就应该在安装依赖中声明。

依赖配置建议：

| 项目 | 说明 |
|------|------|
| 依赖制品 | 选择当前应用运行前必须存在的制品 |
| 版本要求 | 有兼容性要求时写清楚最低版本或推荐版本 |
| 安装与复用 | 检查依赖的安装参数、版本以及是否可以复用已有实例 |
| 安装顺序 | 有顺序要求时在说明中写清楚 |

### 子应用

制品可以添加子应用。子应用适合一个制品内包含多个后端服务的场景，例如主 API 服务、任务服务、回调服务或独立 worker。

子应用的配置方式和主应用一样，也需要先选择代码配置类型：原生应用配置应用配置、启动参数设置、网关域名转发设置和安装依赖；传统应用配置环境类型、环境版本、代码包和 CMD；K8sYaml 上传 Helm 包和额外 YAML。子应用是否需要前端菜单，仍然取决于是否配置管理端、前端包和菜单入口。

### 依赖和子应用的核对要点

启动参数应有明确标题、说明和默认值。敏感值不要写成公开默认值。参数中引用子应用时，编辑值可能采用 `app[i]`；安装信息生成阶段才解析成实际标识。

内置子应用有自己的 `<子应用>/manifest.yaml`，最终进入根 Chart；普通外部依赖通过来源和版本声明，不等于把远端 Chart 直接当成本地子应用。导入远端子应用会先获取内容，再由 UI 分步保存；出现错误应核对已有文件，导入不是原子事务。

`application.order` 用于应用排序及相关引用，不能据此保证服务启动顺序。外部依赖会补充隐藏的 `*_RELEASE_NAME` 参数供安装阶段传递实例名称。

`registerSite` 还可能引入自动 Sidecar；它与普通安装依赖不是同一种机制。集群权限及站点注册策略会同步给内置子应用。

## 配置代码包和变量传递

使用本地静态页面时上传构建后的前端 ZIP，确认入口与资源路径；使用外部页面时配置地址。填写角色、菜单、打开方式与后端关联。

MicroApp 的生成条件是存在 `web.url` 或至少一项 binding 有菜单，因此没有前端 ZIP 也可能存在入口；有 ZIP 也不代表菜单和权限配置正确。

![前端包配置](/examples/zpk/04-frontend-package.png)

后端目标、端口、请求头、Query 与传入前端的属性用途不同。当前 iframe 配置分支只处理其支持的 Query 转发，不应照搬普通内部应用的任意请求头配置。角色可见性也不能代替应用后端鉴权。

| 配置项 | 说明 |
|--------|------|
| 上传代码包 | 上传构建后的前端产物压缩包；压缩包根目录应能找到入口文件 |
| 控制台入口 | 面板打开应用时访问的前端路径，需和前端路由配置一致 |
| 角色 | 控制哪些角色可以访问该入口，默认不要给无关角色开放 |
| 支持 iframe | 应用需要被嵌入面板时开启；如果应用主动跳转顶层窗口，需要先适配 |
| 接口地址 | 前端调用应用自身 API 的地址；后端转发关系以网关域名转发设置为准 |
| 请求头 | 仅传递应用必需的认证和项目上下文，iframe 不支持任意请求头转发 |
| Query | 传递轻量参数，避免放敏感信息 |

变量传递要保持最小化。比如前端只需要面板 API 地址和应用 token，就不要额外传递完整用户信息、调试开关或集群凭据。

## 提交并发布

配置完成后检查菜单配置。需要面板内入口时，添加一级菜单并设置菜单名称、路径和权限。

确认信息无误后点击“确定提交”。提交后回到版本管理或发布设置页，完成版本发布操作。发布前重点检查：

- 制品标识和版本号是否正确。
- 后端包、前端包或 YAML 是否已上传。
- 代码配置类型是否选择正确，传统应用和 K8sYaml 是否跳过了原生应用配置。
- K8sYaml 的 Helm 包、安装配置和额外 YAML 是否属于同一版本。
- 入口菜单、接口地址、网关域名转发规则是否和应用实际路径一致。
- 启动参数、网关域名转发规则、安装依赖和环境变量是否适用于生产环境。
- 子应用是否已按主应用相同的代码配置类型规则补齐配置。
- 版本说明是否能让用户理解本次更新内容。

菜单配置建议：

| 配置项 | 说明 |
|--------|------|
| 一级菜单 | 应用有独立管理页面时添加；纯后端能力通常不需要菜单 |
| 菜单名称 | 使用用户能理解的业务名称 |
| 菜单路径 | 和前端路由入口一致，避免发布后打开空白页 |
| 权限角色 | 和前端包配置中的角色保持一致 |

发布前建议执行一次完整预览：

1. 从版本管理页确认开发版本配置完整。
2. 检查网关域名转发设置，确认后端请求路径、转发目标和匹配规则正确。
3. 确认前端入口和菜单路径一致。
4. 确认发布设置中的目标版本是本次要发布的版本。
5. 提交发布后，在应用市场或安装入口验证版本是否可见。

![提交配置](/examples/zpk/05-submit-publish.png)

## 发布后验证

1. 对最终业务 Chart 执行 lint/render，检查镜像、参数、存储、权限、菜单及子应用。
2. 从面板安装，核对参数表单、外部依赖和实际资源状态。
3. 打开菜单，验证静态文件、前端路由、后端转发和账号权限。
4. 从已发布旧版本升级，核对数据、配置及脚本执行。
5. 验证卸载影响，特别是持久存储和插件修改的文件。

下架版本会尝试重发更早的已发布记录，不会自动回退集群里的已安装版本。已交付给用户的版本出现不兼容问题时，应新建修复版本并说明迁移影响。

| 验证项 | 预期结果 |
|--------|----------|
| 应用市场可见 | 应用名称、图标、版本号和描述显示正确 |
| 安装流程 | 安装参数、默认值和必填项符合预期 |
| 后端服务 | Pod 正常运行，健康检查通过，日志无启动错误 |
| 前端入口 | 菜单能打开页面，iframe 或微应用加载正常 |
| API 请求 | 前端能访问应用 API，网关域名转发规则、请求头和 Query 参数生效 |
| 子应用 | 子应用实例、端口、转发规则和依赖关系符合配置 |
| 升级流程 | 从旧版本升级到新版本后配置不丢失 |

## 常见问题

| 问题 | 核对方向 |
| --- | --- |
| 标识不通过 | 区分网页两段输入和后端多段横线格式，避免下划线和其他符号 |
| 菜单不显示 | 检查 web.url、binding.menu、角色、发布结果及面板安装资源 |
| 前端空白 | 检查 ZIP 层级、入口路径、静态资源地址和代理响应 |
| 发布后仍在处理中 | 重新加载版本页，检查 worker 日志和最终状态 |
| 推送成功但不能安装 | OCI 推送只入库，继续核对发布和运行 Chart |
| 安装包地址为空 | 检查运行 Chart 和动态转换日志，不能只判断 Info 的 HTTP 状态 |

本页流程依据源码静态追踪；本次文档更新未执行上述集群验证。
