# 镜像管理

镜像管理更偏向节点侧运维，主要处理镜像准备、镜像导入整理和本地镜像相关问题。它适合排查“应用为什么拉不到镜像”或“节点上镜像是否已经准备好”这类问题。

在当前面板里，镜像相关能力不只有 **镜像管理** 列表页，还包含一个隐藏的 **构建镜像** 链路，用来处理更进一步的镜像构建场景。

## 进入镜像管理

1. 登录微擎面板。
2. 在左侧菜单进入 **集群管理**。
3. 点击 **镜像管理**。

如果你处理的是“节点上已有镜像怎么看、镜像是否准备好”，通常从 **镜像管理** 开始；如果你处理的是“镜像如何被构建出来”，则还需要进入后续的 **构建镜像** 相关页面或流程。

## 适合什么场景

常见场景包括：

- 查看节点侧已有镜像
- 确认镜像是否已经存在
- 排查镜像拉取相关问题
- 处理本地镜像导入、整理或提交
- 结合构建型应用或节点侧镜像准备做进一步维护

如果应用部署失败、镜像构建异常，或者你怀疑问题出在节点镜像侧，通常就应该优先进入镜像管理。

## 进入后先看什么

通常建议优先确认：

- 目标镜像是否已经存在
- 镜像标签是否正确
- 节点侧镜像是否处于可用状态
- 当前问题是“镜像不存在”还是“镜像有了但应用仍然异常”

列表中镜像 ID 作为辅助信息显示在镜像名称下方，用于区分同名标签对应的实际镜像内容。

## 本地镜像管理什么时候会用到

本地镜像管理更适合这些情况：

- 需要把镜像导入到当前集群环境
- 需要整理已有本地镜像
- 需要确认应用依赖的镜像是否已经就位
- 需要从运行中的容器进一步生成镜像或处理镜像结果

如果你的环境并不完全依赖外部镜像仓库，这部分能力会很实用。

### 使用示例：准备和导入镜像

如果程序提供者已经给了镜像归档文件，可以直接上传。需要自己准备时，在已安装 Docker、并能下载镜像的电脑或服务器上执行：

```sh
docker pull nginx:1.28
docker save -o nginx-1.28.tar nginx:1.28
```

第一条下载镜像，第二条将它保存为当前目录下的 `nginx-1.28.tar`。这与网站源码 ZIP 不同，也不要用 `docker export` 代替。

在面板镜像导入入口选中目标服务器，镜像地址的目录填写 `demo`，名称与版本填写 `nginx:1.28`，再上传这个 tar 文件。当前页面固定的地址前缀是 `registry.local.w7.cc/`，因此本例导入后的完整名称为 `registry.local.w7.cc/demo/nginx:1.28`。完成后刷新该服务器的镜像列表，核对实际完整名称；应用中也填写这个名称。其他服务器需要分别导入或能够从仓库下载，导入到一台不会自动分发到全部节点。

### 导入结果和固定保留

需要导入本地镜像时，准备符合要求的镜像文件，按页面提供的导入入口操作，等待完成后再确认应用使用的名称和版本。

导入结束后刷新列表，核对程序包名称和版本都正确；上传完成不等于镜像已经导入成功。

页面中的 **PINNED** 表示把镜像设为固定保留，避免被自动清理，不等于已做备份。

需要删除镜像时，先确认是否仍有应用使用它。删除后，后续启动可能需要重新下载。

“构建镜像”是把代码和运行环境制作成程序包，适合开发者使用。直接从应用商店安装应用时，通常不需要自己构建。

## 构建镜像什么时候会用到

如果你的目标不是确认节点上“有没有镜像”，而是要把代码包、制品或构建结果进一步变成可用镜像，这时通常会进入 **构建镜像** 相关流程。

可以简单理解成：

- **镜像管理** 更偏查看、导入、整理和确认镜像状态
- **构建镜像** 更偏把内容实际构建成镜像结果

## 镜像相关问题怎么判断

如果应用部署异常，建议先从这几个方向判断：

1. 目标镜像名称和标签是否正确
2. 节点侧是否已经存在该镜像
3. 镜像准备是否正常完成
4. 问题在镜像侧，还是在应用启动后的其他环节

很多时候，应用异常的根因并不在配置本身，而是在镜像根本没有准备好。

### 下载失败的检查步骤

1. 在应用事件中查看失败原因。
2. 核对镜像名称和版本是否存在。
3. 私有仓库需要确认账号和下载权限。
4. 让管理员检查运行该应用的服务器能否连接下载地址，必要时调整镜像源。

如果镜像已下载但应用仍报错，继续查看应用日志和配置。

## 使用镜像管理时的建议

- 先确认问题是不是镜像侧，再进入镜像管理
- 处理镜像前，先核对镜像名和标签
- 如果涉及导入、提交或整理，最好先明确目标用途
- 不要把应用启动问题和镜像准备问题混在一起判断

镜像管理的价值，是让你更快判断节点镜像侧是否已经准备就绪，并把镜像相关问题和应用层问题分开看清楚。
